# План оптимизации задержки `transono`

Цель: снизить заметную задержку аудиопотока. Работа ведётся **аддитивно** — старые
пути не ломаются, новые добавляются рядом (feature-flag / новый вариант API).

Ссылки на исходники даны по состоянию на момент анализа.

---

## Часть 1 — Фиксированные буферы и квант выдачи

Убирает ~35–40 мс с прямого пути (микрофон → сплиттер → микшер → вирт-микрофон)
и ~21 мс с выхода перевода.

### 1.1 — Общая константа целевой задержки
Новый модуль `src/audio/latency_config.rs` (или добавить в `src/audio/mod.rs`):

```rust
/// Целевая аппаратная задержка на направление, мс.
pub const TARGET_LATENCY_MS: u32 = 10; // 480 @ 48k ≈ 10 мс, 256 ≈ 5.3 мс

/// Число фреймов под целевую задержку для данной частоты.
pub fn latency_frames(sample_rate: u32) -> u32 {
    (sample_rate * TARGET_LATENCY_MS / 1000).max(1)
}
```

Одно место правды для подстройки.

### 1.2 — `input_cpal.rs::select_config` → `BufferSize::Fixed`
Файл: `src/audio/cpal/input_cpal.rs:198-206`
Заменить `buffer_size: BufferSize::Default` на
`buffer_size: BufferSize::Fixed(latency_frames(cfg.sample_rate()))`.

**Защита (additive):** не все устройства/host принимают `Fixed`. Обернуть
`build_input_stream`/`build_output_stream` так, чтобы при ошибке с `Fixed`
повторить попытку с `Default` (лог в stderr), не ломая рабочий путь.

### 1.3 — `output_cpal.rs::select_config` → `BufferSize::Fixed`
Файл: `src/audio/cpal/output_cpal.rs:209-218` — то же самое
(`BufferSize::Fixed(latency_frames(...))`).

**Trade-off:** слишком маленький фикс на выходе → андерраны (щелчки), если питание
не успевает. Но лидер = оригинал приходит раньше перевода, питание стабильное, поэтому
`Fixed(480)` (~10 мс) безопасно; `256` (~5 мс) — если на стенде без щелчков.
Рекомендуемый выбор для утверждения: **`Fixed(480)`** (надёжнее), опц. `Fixed(256)`.

### 1.4 — Микшер: убрать `sleep(1ms)`
Файл: `src/runtime/mixer.rs:234-237` (ветка «не готово»):
```rust
tokio::time::sleep(Duration::from_millis(1)).await;
```
заменить на:
```rust
tokio::task::yield_now().await;
```
Снимает лишнее квантование выдачи лидера (~1 мс) и «залипание» таска на 1 мс каждый
пустой цикл.

### 1.5 — Окружение (вне кода)
На стенде понизить квант самого PipeWire: `PIPEWIRE_LATENCY=48/256` (≈5.3 мс) либо
настроить quantum в конфиге сервера. Дефолтный серверный quantum ~10–20 мс.

**Ожидаемый эффект части 1:**
- прямой путь ~45–55 мс → ~10–15 мс;
- выход перевода ~21 мс → ~10 мс.
Риск: андерраны при слишком агрессивном `Fixed` (купируется fallback + выбор 480).

## Часть 2 — Переход на более быстрый движок каналов

Текущий горячий путь использует `tokio::sync::mpsc` (аллокирующий, с блокировками,
async-планировщиком) во всех звеньях: splitter → outputs, link, input/output streams,
сессии. Это даёт планировщик-джиттер и аллокации `Audio` на каждый прыжок.

### Обсуждение: `kanal` / `crossbeam-channel` против `rtrb`
- Горячий путь почти везде **SPSC** (1 producer → 1 consumer): splitter outputs,
  `AudioLink::new_link`, input/output CPAL streams. Для SPSC оптимальны `rtrb`/`ringbuf`
  (lock-free, zero-alloc, zero-copy `try_send`/`try_recv`). `kanal`/`crossbeam` — это
  **MPMC**, несут оверхед, здесь не нужный.
- `crossbeam`/`kanal` — синхронные API, в tokio их нельзя просто `.await`; нужен
  poll-цикл или `spawn_blocking`. `tokio::sync::mpsc` даёт корректный backpressure.
- **Вывод:** не переключать горячий путь на `kanal`/`crossbeam`. Использовать `rtrb`
  (уже в `Cargo.toml`) для SPSC-звеньев. MPMC-каналы уместны только при появлении
  настоящего сценария (пул воркеров, конкурирующих за один аудио-канал).

### Варианты
- **A — `rtrb` на всех SPSC-звеньях** (рекомендуемый старт). Заменить `tokio mpsc` на
  `rtrb::RingBuffer` в splitter outputs, `AudioLink::new_link`, input/output CPAL streams.
  Микшер уже опрашивает через `now_or_never()` → ложится на `try_recv` без изменений.
  Плюсы: zero-alloc, нет блокировок, минимум джиттера. Минусы: клон `Audio` в splitter
  остаётся, типажи `Stream`/`Sink` надо заменить на poll-обёртки.
- **B — Специализированный broadcast-ring для сплиттера.** _[ОТЛОЖЕНО]_ Один вход → N выходов сейчас
  клонирует `audio` на каждый output. Сделать shared broadcast ring с атомарными
  курсорами (write cursor + per-consumer read cursor), сэмплы лежат один раз. Клонов нет.
  Добавить после A, если профиль покажет, что клонирование в сплиттере дорого.
- **C — Полностью lock-free граф** (rtrb + broadcast) + poll-интерфейс вместо _[ОТЛОЖЕНО]_
  `futures::Stream` для максимальной детерминированности (убрать async-планировщик из
  горячего пути). Самый большой рефактор, ломает текущие `BoxStream`/`BoxSink`.
- **D — Слить splitter + mixer + link в один таск** (убрать промежуточные каналы). _[ОТЛОЖЕНО]_
  Минимум прыжков, но крупный рефактор и потеря модульности графа.

**Рекомендация:** начать с **A**, затем при необходимости **B**. C и D — только если
A/B не хватит.

### 2.1 — Логическая композиция каналов (fusion) — новая идея
Концепт: если consumer канала живёт в том же контексте, что producer, не создавать
промежуточный канал — producer пишет напрямую в буфер consumer (или вызывает его
обработчик). Это «operator fusion / channel elimination», как в аудио-движках.

Применение в `transono`: `AudioLink::new_link` (`src/runtime/link.rs:49-89`) — это
identity-узел: читает из одного mpsc и пишет в другой mpsc + отдельный `tokio::spawn`.
В бинаре такая цепочка (mixer.out → link → virt-mic; to_mixer → link → mixer и т.д.).
Каждый канал `capacity=32` и кадр 5 мс даёт до ~160 мс capacity-задержки + переключение
контекста. 10 последовательных link = 10 пар каналов, 10 тасков.

С fusion: один общий ring + один обработчик, применяющий цепочку «на лету». Задержка
падает до размера одного кадра (~5 мс), тасков меньше.

**Как сделать аддитивно:** добавить новый вариант (например `AudioLink::new_fused` или
автодетект), не трогая старый `new_link`. При построении графа, если Link соединяет два
endpoint-а, которые можно сшить, Link не создаёт новый mpsc, а даёт consumer читать из
того же `rtrb::RingBuffer` (shared ring) либо регистрирует direct-wire:
`producer.write(x)` вызывает `consumer.accept(x)` напрямую.

**Ограничения fusion:**
1. Разные потоки (CPAL input/output callbacks) нельзя слить без смены модели ввода/вывода
   — здесь канал как граница потока необходим. Fusion только внутри tokio-тасков
   (mixer→link→virt-mic всё в tokio, сшить можно).
2. Stateful DSP с lookahead (ресемплер `src/audio/processors/resampler.rs`, накопление
   20 мс) нельзя in-place слить с соседом без промежуточного буфера. Fusion применим к
   *простым pass-through звеньям* (link, splitter-output→input), не к DSP-пайплайнам.
3. Канал сглаживает всплески (capacity); убрав его, медленное звено будет блокировать
   цепочку (или дропать). Решить явно: оставить маленький ring (capacity=4 ≈ 20 мс) для
   сглаживания, либо strict in-place.

**Шаги части 2:**
- 2.1: заменить SPSC `tokio mpsc` на `rtrb` (вариант A) — база. **[ВЫПОЛНЕНО — интерактивно подтверждено: прямой звук без задержек]**
- 2.2: добавить fused link для pass-through звеньев (mixer→virt-mic, to_mixer→mixer) — _[ОТЛОЖЕНО]_
  убрать лишние каналы/таски, сшить через shared ring или direct-wire.
  Причина откладывания: задержка уже устранена 2.1; fusion несёт риски (back-pressure между
  звеньями на разной скорости, переделка ownership/shutdown/drain, сложная отладка без границ
  линков), выгода не доказана профилем.
- 2.3 (опц): splitter → fused broadcast-ring (вариант B), убрать `audio.clone()` на _[ОТЛОЖЕНО]_
  каждый output. Причина: `Audio::clone()` — это Arc-копия (дёшево, не копия буфера), не
  является узким местом (проверено).
