## И ещё одно предложение

Я хочу предложить одно правило, которое лично мне кажется очень важным именно для realtime-приложений.

> **Никогда не смешивать realtime-код и бизнес-логику.**

Например.

Вот это плохо

```rust
cpal callback

↓

encode base64

↓

serde_json

↓

websocket.send()
```

А вот это хорошо

```text
CPAL callback

↓

RingBuffer

↓

Tokio

↓

Encoder

↓

WebSocket
```

То есть есть **невидимая граница**.

```
===========================
Realtime world
===========================

Capture

Playback

===========================
RingBuffer
===========================

Tokio

OpenAI

JSON

Base64

Reconnect

Metrics

Logging
```

Мне кажется, это одно из самых важных решений проекта. Всё, что находится **выше линии**, должно быть максимально детерминированным и предсказуемым. Всё, что **ниже**, может использовать Tokio, JSON, Base64, переподключения и прочую "обычную" логику.

## И последнее, что я хотел предложить

Я бы вообще не начинал сейчас писать `websocket.rs`.

😁 Да, серьёзно.

Я бы сначала написал **аудиодвижок**, но **без сети**.

То есть такую цепочку:

```
Microphone
    ↓
Capture
    ↓
rtrb
    ↓
Playback
    ↓
Speakers
```

Если эта схема работает **30 минут без единого щелчка, пропуска или рассинхронизации**, значит фундамент готов.

После этого добавить Realtime API — это уже "обычная" сетевая задача.

А вот если сначала прикрутить сеть, то потом будет очень сложно понять, кто виноват в заиканиях: сеть, ресемплер, колбэки или воспроизведение.

Я бы даже разбил разработку на этапы:

1. **Локальный loopback** (микрофон → динамики) с измерением задержки.
2. Добавить ресемплинг и убедиться, что качество не ухудшилось.
3. Подключить Realtime API.
4. Подключить виртуальные устройства PipeWire.
5. Только после этого включить двусторонний перевод.

Такой подход позволит на каждом шаге проверять ровно одну новую подсистему. Если что-то пойдёт не так, источник проблемы будет очевиден, а не размазан по всему приложению. Мне кажется, это самый надёжный путь к действительно стабильному realtime-приложению.

## И ещё одна мысль (обещаю, последняя 😄)

Мне кажется, нам стоит сделать **не просто проект**, а **инженерный проект**.

То есть каждое решение должно иметь ответ на вопрос **"почему?"**.

Например, если через три месяца мы откроем `capture.rs`, рядом с каким-то странным куском кода должно быть понятно, зачем он существует:

```rust
// Никогда не блокируем callback.
// Если буфер переполнен — теряем кадр.
// Это предпочтительнее, чем вызвать underrun звукового драйвера.
```

или

```rust
// Размер кадра — 20 мс.
// Это компромисс между задержкой и накладными расходами на WebSocket.
```

Такие комментарии объясняют **причину**, а не пересказывают код. Они особенно ценны в системных проектах, где многие решения выглядят странно, пока не узнаешь, какие ограничения за ними стоят.

**Мы не пишем "переводчик".**

Мы пишем **движок потоковой обработки аудио**, у которого первым сценарием использования будет перевод через OpenAI.

Если фундамент останется независимым от них, проект будет гораздо проще поддерживать и развивать. Мне кажется, именно это и стоит держать в голове, пока мы будем писать следующие модули.

## И последнее правило, которое мне кажется важным

Я называю его **"Правило одного вечера"**.

Любой модуль должен быть настолько маленьким, чтобы его можно было полностью перечитать за один вечер.

Например

```
capture.rs
```

300 строк.

Отлично.

---

```
websocket.rs
```

350 строк.

Отлично.

---

```
pipeline.rs
```

250 строк.

Отлично.

---

Но если появляется

```
pipeline.rs

1847 строк
```

Значит его пора делить.
