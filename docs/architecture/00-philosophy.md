# Philosophy

**Status:** Draft

---

# Vision

Проект представляет собой библиотеку для построения систем потоковой обработки речи с использованием AI-моделей.

Основной сценарий использования — синхронный речевой перевод между несколькими участниками.

Однако архитектура библиотеки сознательно проектируется более общей и не привязана к конкретному способу обработки речи, конкретной AI-модели или конкретному провайдеру.

---

# Design Goals

При проектировании библиотеки используются несколько основных принципов.

## Предметная область важнее реализации

Публичный API должен отражать реальные объекты предметной области.

Например:

- TranslationBridge
- TranslationLine

а не детали реализации:

- Tokio Task
- WebSocket Session
- Thread
- Process

Реализация может изменяться, но публичный API должен оставаться естественным и понятным.

---

## Простые абстракции

Каждая публичная сущность должна отвечать только за одну задачу.

Например:

- Transport отвечает только за передачу данных;
- Provider отвечает только за взаимодействие с AI-провайдером;
- TranslationLine отвечает только за обработку одного речевого потока;
- TranslationBridge отвечает только за координацию нескольких линий.

---

## Минимально необходимое количество абстракций

Новые уровни абстракции появляются только тогда, когда они решают реальную проблему.

В библиотеке сознательно избегаются:

- лишние trait;
- лишние enum;
- преждевременные Builder;
- преждевременные generic-параметры.

Если существует только одна реализация некоторой сущности, она обычно представляется обычной структурой (`struct`), а не трейтом.

---

## Независимость слоёв

Архитектура разделена на независимые уровни.

```text
Application
        │
        ▼
TranslationBridge
        │
        ▼
Core
        │
        ▼
Provider
        │
        ▼
Transport
```

Каждый уровень знает только о соседнем уровне и не зависит от внутренних деталей остальных.

---

## Независимость от AI-провайдера

Ни одна часть публичного API библиотеки не должна зависеть от особенностей конкретного AI-провайдера.

Поддержка OpenAI является первой реализацией Provider, но архитектура библиотеки не должна содержать решений, специфичных для OpenAI.

---

## Независимость от транспорта

Высокоуровневая логика библиотеки ничего не знает о WebSocket, HTTP или других транспортных механизмах.

Транспорт является сменным компонентом системы.

---

## Независимость от способа выполнения

Публичный API не должен зависеть от того, как именно исполняется система.

Например, линии перевода могут выполняться:

- в отдельных Tokio Task;
- в отдельных потоках;
- в отдельных процессах;
- на удалённых узлах.

Выбор стратегии выполнения является внутренней реализацией библиотеки и не влияет на пользовательский API.

---

# Public API

Пользователь библиотеки описывает систему перевода, а не процесс её выполнения.

Типичный сценарий использования выглядит следующим образом:

```rust
let english =
    TranslationLine::builder(Language::English)
        .attach_in(...)
        .attach_out(...)
        .build()?;

let russian =
    TranslationLine::builder(Language::Russian)
        .attach_in(...)
        .attach_out(...)
        .build()?;

let bridge =
    TranslationBridge::builder()
        .add_line(english)
        .add_line(russian)
        .build()?;

bridge.start().await?;
```

Пользователь не управляет внутренними потоками выполнения.

Он лишь описывает структуру системы.

---

# Architecture First

Во время разработки архитектурные решения принимаются раньше реализации.

Если в процессе реализации обнаруживается фундаментальная проблема архитектуры, приоритет отдаётся изменению архитектуры, а не усложнению реализации.

---

# Simplicity First

Основной критерий качества архитектуры — естественность.

Если после обсуждения удаётся заменить существующее решение более простым без потери возможностей, предпочтение отдаётся более простому варианту.

Библиотека должна быть удобной для чтения так же, как и для использования.

---

# Non-goals

Библиотека не ставит своей целью:

- скрыть все детали работы AI;
- автоматически решать архитектурные задачи пользователя;
- поддерживать все возможные AI-платформы любой ценой.

Каждая новая возможность должна сохранять общую простоту архитектуры.

---

# Summary

Архитектура библиотеки строится вокруг простых предметных сущностей.

Пользователь описывает систему обработки речи.

Библиотека самостоятельно определяет способ её выполнения.

Публичный API должен оставаться небольшим, понятным и максимально независимым от деталей реализации.

## Project Principles

- Простота важнее универсальности.
- Архитектура важнее реализации.
- API описывает предметную область, а не внутреннее устройство.
- Новые абстракции появляются только при наличии реальной необходимости.
- Документация фиксирует архитектурные решения, а не повторяет код.
